# 方法论

这里记的是**反直觉但正确**的结论，全部是踩出来的。
改这套工具之前先读一遍，否则很容易「优化」回错误的做法。

## 数据与判断必须分离

每张表都要标明：哪些是**数据**（原样读取，不可争论），
哪些是**判断**（可以争论，必须写明理由）。

例如点位表里，`eBird locId` 是数据（从 API 原样读出），
而 `lat/lon/半径` 是判断（按地图估的，不是官方边界）。
混在一起，三个月后没人说得清哪个数字可以改。

**判断必须写为什么。** 一张没有理由的判断表，下一个人只能原样照抄或全部推翻。

## 频次 ≠ 难度

eBird 频次回答的是「**在不在**」，不是「**好不好找**」。

实测反例：
- 某地鸫在某保护区记录很多，但专业团队实测耗了三天才看到；
- 某鸡鹑过去极难，建了隐蔽棚之后变成「坐着等」。

所以频次高不等于轻松，频次低也不等于没戏。
**记录数回答在不在，现场经验回答好不好找，两列要一起看。**

## 「没数据」≠「看不到」

这是最容易把预测做错的地方。

远洋海鸟在所有陆基热点上的频次都是 **0**——
不是那儿没有，而是它们是在**船上**看的，船上的记录不会落进港口热点的清单。
把这些 0 当成「看不到」，预期种数会凭空变低。

所以：**无数据的种单列成节，不进点估计**，并写明三类可能原因
（结构性盲区 / 本就罕见 / 点位不覆盖）。

同理，GBIF 的 0 常常是**分类骨干滞后**——近年新拆分的学名只能匹配到属级，
真实存在的种会显示成全区 0 条。**不要拿任何源的 0 去否定一件事。**

## 零记录可以否决，但要有证据

「有效机会」的规则演化过三版，第三版才站得住：

1. **只看 GBIF ≥20 条** —— 新拆分的学名全岛 0 条，真实存在的种被判成没机会。
2. **GBIF ≥20 或 eBird ≥15%，取并集** —— GBIF 按半径圈，
   邻近生境被算进来。实测出过：出海点的 30 km 半径把内陆水体的淡水鸭算了进来，
   把人指向了错误的地点。
3. **并集 + 零记录否决**（现行）—— eBird 在该点有**足够样本**却零报到，
   则否决 GBIF 的主张。

关键区分：
- **低频 ≠ 不存在**。38 天里报到 2 次是「少见但确实有」，**保留**；
- **零记录 + 足够样本 = 有证据的不存在**，**否决**。

## 总种数会误导，要同时看特有种

实测这趟行程：

| 情景 | 总种数 | 特有种 |
|---|---:|---:|
| 丢掉滨海湿地 | **-26** | -0.1 |
| 丢掉低地雨林 | -14 | **-8.1** |

按总种数排，滨海湿地的影响几乎是雨林的两倍；
但这趟真正的命脉是 35 种特有种，而它们几乎全在雨林一侧。
**丢掉湿地损失的是「数量」，丢掉雨林损失的是「目标」。**

只排一个指标会把资源投错地方。所以敏感性表默认按**特有种**排序。

## 区间表达运气，敏感性表表达风险

概率模型的 80% 区间只含**独立随机性**。
但现实里各时段不独立：连日大雨同时毁掉所有时段，鸟导水平同时影响全程。

这种相关性**刻意不进方差**——否则区间会假装自己涵盖了它。
改用场景表单独说。**两个要一起看：点估计脱离区间和敏感性表就是虚假精确。**

## 模型的天花板必须印出来

eBird 频次的分母「观鸟日」是**该点位当天所有观察者、所有热点的清单并集**，
不是一个人的一次外出。所以单个时段的当量**封顶 1.0**：
一队人最多拿到「全站一天」的量，不可能超过。

这个 bug 是被**通用性验收**抓出来的：
泰国 2 天 3 个时段预测出 231 种，而斯里兰卡 10 天预测 215 种看着完全合理。
**单一样本会掩盖模型错误，换个地区才暴露。**

修完还发现偏差方向**因地区而异**：

| 点位 | 一个观鸟日的期望种数 |
|---|---:|
| 低地雨林（林内难看、清单短）| 32 |
| 被密集覆盖的山地国家公园 | 156 |

同一个模型在前者偏保守、在后者偏乐观。
与其调一个说不清的全局系数，不如**把 `Σfreq` 天花板诊断印进输出**，
让用户自己判断该打几折。

## 校准要留痕，不静默调参

参数改动必须写进 `checks.md`：改前、改后、理由。
参考行程的实测总数用来**判断模型偏向**，不用来自动修正参数——
自动修正会让模型变成「拟合某一趟」，换个行程就不知道准不准。

## 夜间数据：诚实地说「数据只够说这些」

eBird 频次**按点位统计，不含时段信息**，一份 2 月的清单绝大多数是白天提交的。
把它原样套到夜探时段上，会把白天的全部种重复列一遍
（实测某 safari 点的夜探段曾原样重复了白天的 132 种）。

诚实的做法：**夜间时段只列夜行类群**，并写明
「这不是说夜里只有这些鸟，而是数据只支持对这些鸟下结论」。
反过来**白天不排除夜行类群**——鸮类白天在 roost 被定点是常规操作。

## 名字是最危险的一环

判断文本大量由 LLM 从外部物料里读出来，物料里的鸟名五花八门：
老图鉴叫法、带连字符的、属名已被拆分的、中文俗名。

**只要有任何一处允许「凭名字直接写进文档」，就一定会出现编造或张冠李戴的鸟名**——
而鸟名错一个字母，当地鸟导就查不到这只鸟。

所以：
1. 任何外部名字必须先过 `taxonomy.resolve()` 变成 eBird `speciesCode`；
2. 判断文本里提到鸟只能写 `{{code}}` 占位，渲染时注入；
3. 解析不出的进 `unresolved`，**由人裁决，脚本绝不猜**；
4. `verify.py` 反查产出文档里的每个加粗英文名是否来自 eBird/IOC。

这道闸门在开发过程中**抓住了作者本人三次**：
凭印象写的 `srlgrp1`、`srlhap1` 两个 code 根本不存在，
`白燕鸥` 填了 `whiter3`（大西洋种，本地区名录没有）而正确的是 `whiter4`。

同理，手写的名单也会错。用户提供的 35 种特有种名单里有 3 处缺陷：
「红背啄木鸟」解析到南美的 Crimson-mantled Woodpecker、
「棕鸫鹛」解析到印度种、「斯里兰卡林鵙」带了个错字。
**eBird 原生判定独立算出的 35 种才是对的。**

## 确定性：无序遍历 set 会让文档漂移

实测过：同样的输入连续三次生成出三份不同的文档。
原因是遍历 `set` 的顺序在不同进程间不保证。

一律 `sorted()`。`verify.py` 有专项检查扫描生成器源码。

## 校验不能代替一键构建

校验脚本只读产出的 `.md`，**发现不了生成器崩了**。
实测踩过：生成器抛异常退出、文档停在旧版本，而校验照样全绿——
因为它校验的是上一次成功生成的旧文件。

所以**生成与校验必须串在一起跑**（`engine/build.py`），
任一步非零退出就停，并明确提示「文档可能停留在旧版本」。
